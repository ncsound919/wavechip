# Vector Waves — M0 DSP Runtime

A DSP-first scaffold for the four-corner vector/chip instrument concept. This repository intentionally contains **no designed product UI**. It exposes a framework-independent TypeScript host API so your own React/TypeScript interface can be built independently.

## M0 scope

Included:

- C++17 monophonic wavetable voice compiled to WASM with Emscripten.
- Standard Web Audio `AudioWorklet` host; the C++ DSP is called from the worklet render thread.
- 2048-sample internal single-cycle wavetable format.
- Input resampling from arbitrary single-cycle lengths.
- Eleven FFT-derived harmonic mip levels, selected by oscillator frequency to reduce aliasing.
- MIDI note-on/note-off, amplitude ADSR, one-pole low-pass filter, master gain and fine tuning.
- Seeded drift engine with fixed voice personality, slow wander, a shared-temperature-style component, warm-up, and age scaling.
- Optional SharedArrayBuffer SPSC parameter ring with `MessagePort` fallback.
- Native C++ tests and TypeScript ring-buffer tests.

Not included in M0: vector mixing, wave-sequence lanes, multi-frame tables, chip emulation, chip racks, Chipify, FM/ring-mod fusion, effects, presets, MIDI device I/O, or a visual interface.

## Architecture

```text
Your UI (React / TypeScript / anything)
             |
             v
       VectorWavesEngine.ts
       |             |
       | SAB ring    | MessagePort fallback + note/table events
       v             v
       AudioWorkletProcessor (public/overlay-processor.js)
                        |
                        v
                Emscripten WASM module
                        |
                        v
                   C++ DSP core
            wavetable + mipmaps + ADSR
                 filter + drift
```

The C++ core has no browser, network, UI, storage, or chip-library dependencies. Native CMake tests exercise the same source used by the WASM build.

### Why a standard AudioWorklet wrapper?

Emscripten's dedicated Wasm AudioWorklet API uses its Wasm Workers/shared-memory model. This scaffold instead uses a standard browser AudioWorklet to host an Emscripten-built module. It keeps synthesis in the audio rendering thread but makes the parameter transport optional: SharedArrayBuffer when the page is cross-origin isolated, otherwise MessagePort. The Emscripten output is built as a single-file module because AudioWorkletGlobalScope does not provide the normal fetch path for loading a separate `.wasm` file.

## Requirements

- Node.js 20.19+ or 22.12+ (Node 22 recommended).
- npm.
- Emscripten SDK (`emcc`) available on `PATH`, or set `EMCC=/path/to/emcc`.
- CMake 3.20+ and a C++17 compiler for native tests.
- A browser with AudioWorklet and WebAssembly support.

## Setup

```bash
npm install
```

Build the WASM module:

```bash
npm run build:wasm
```

This writes `public/wasm/overlay-dsp.js`. The generated file is intentionally ignored by git and must be generated before the production build.

Start the Vite host:

```bash
npm run dev
```

Build the web assets:

```bash
npm run build
```

Run the native C++ tests:

```bash
npm run test:native
```

Run TypeScript tests:

```bash
npm test
```

Run the full checks that do not require Emscripten:

```bash
npm run check
```

## UI integration

Import the engine from `src/index.ts`. Create and resume the `AudioContext` from a user gesture in your own UI, then instantiate the engine.

```ts
import { VectorWavesEngine } from './index';

const context = new AudioContext();
await context.resume(); // call in response to a user gesture

const engine = await VectorWavesEngine.create(context, { seed: 12345 });
engine.connect(context.destination);

engine.setParameter('masterGain', 0.2);
engine.setParameter('filterCutoffHz', 9000);
engine.noteOn(60, 0.9);

// Optional: send one normalized cycle. The core resamples it and builds mips.
const cycle = new Float32Array(2048);
for (let i = 0; i < cycle.length; i += 1) {
  cycle[i] = Math.sin((i / cycle.length) * Math.PI * 2);
}
await engine.loadWavetable(cycle);

// Later:
engine.noteOff();
await engine.dispose();
```

`PARAMETERS` is exported as metadata for building your own controls. The engine clamps all incoming values to the matching parameter range. `VectorWavesEngine` also exposes `ready`, `usesSharedParameterRing`, and `addEventListener()` events (`ready`, `error`, `wavetableloaded`).

### Parameter inventory

| Parameter | Range | Default | Notes |
|---|---:|---:|---|
| `masterGain` | 0–1 | 0.25 | Linear output gain |
| `tuneCents` | -24–24 | 0 | Global tune offset in cents |
| `attackSeconds` | 0.001–5 s | 0.01 s | ADSR attack |
| `decaySeconds` | 0.001–5 s | 0.25 s | ADSR decay |
| `sustainLevel` | 0–1 | 0.8 | ADSR sustain |
| `releaseSeconds` | 0.001–10 s | 0.25 s | ADSR release |
| `filterCutoffHz` | 80–20,000 Hz | 16,000 Hz | One-pole low-pass cutoff |
| `driftAmount` | 0–1 | 0.15 | Overall drift depth |
| `driftRate` | 0–1 | 0.35 | Maps to 0.05–0.50 Hz |
| `driftSpread` | 0–1 | 0.15 | Fixed voice-personality spread |
| `driftWarmup` | 0–1 | 0.35 | Maps to 15–180 seconds |
| `driftAge` | 0–1 | 0.10 | Additional long-term instability |

M0 is a single voice, so `driftSpread` affects the one voice's deterministic personality. A multi-voice rack will give this parameter its intended between-voice meaning. Cross-voice temperature correlation is a rack-level behavior and is not yet exposed.

## SharedArrayBuffer and deployment headers

The Vite dev and preview servers include:

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

`public/_headers` provides the same headers for static hosts that support the Cloudflare Pages `_headers` format. Your deployment platform must be configured to send equivalent headers for the SAB path. If the browser is not cross-origin isolated, the engine automatically uses MessagePort for parameter changes.

If you later load remote fonts, images, sample files, or other cross-origin assets, make sure they satisfy your COEP policy (for example, by serving same-origin or with compatible CORS/CORP headers). You can force the fallback during development:

```ts
const engine = await VectorWavesEngine.create(context, {
  useSharedParameterRing: false,
});
```

## DSP implementation notes

- Mipmaps are generated at table-load time using an in-core radix-2 FFT; no FFT work occurs in `process()`.
- The worklet preallocates left/right render buffers during initialization. The render callback performs no explicit JS allocations.
- The SAB path is a single-producer/single-consumer integer ring. Parameter values are transported as float bit patterns in atomic 32-bit slots.
- The C++ core uses a fixed-capacity state layout and does not allocate in its render loop.
- Drift is seeded, so the same seed and same event/parameter sequence are reproducible on the same build/runtime. It is an intentional musical instability model, not a claim of exact analog component simulation.

## Known M0 limitations / next engineering tasks

1. Monophonic voice only; no allocator, vector blend, or polyphony.
2. Wavetable load is performed on the worklet's message event. Keep frame sizes modest until an offline preparation/transfer path is added.
3. The initial one-pole filter is a functional placeholder, not a character filter or resonant topology.
4. The oscillator uses linear interpolation. Evaluate cubic interpolation only after profiling; the band-limited mip selection is the primary anti-aliasing control in this milestone.
5. Add browser automation and a render-capture test before calling the WASM/browser pipeline production-ready.
6. Before M1, split `Wavetable`, `DriftState`, `Envelope`, and `Voice` into separate modules and add a voice-slot abstraction so the same DSP contract can host chip instances later.
